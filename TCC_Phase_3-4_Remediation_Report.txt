Scope: Phase 3-4 remediation only. No Phase 5 admin interface was built.

EXECUTIVE OUTCOME

The repository has been moved from browser-authoritative demo behavior toward a customer application with explicit server/database authority. Customer-facing visuals and established routes were preserved. The browser can no longer create authoritative orders, payments, verified measurements, confirmed appointments, wardrobe records, operational notifications, or trusted lifecycle state.

Repository implementation and application verification are complete. The Supabase changes have NOT been deployed to, or tested against, a live project from this workspace. Phase 5 must not begin against a production environment until the migrations, grants, RLS policies, storage policies, and pgTAP tests are applied and verified on the intended Supabase project.

C. RLS CHANGES

Authenticated customers may now:
- Read only their own profile, measurement history, bespoke requests, orders, appointments, payments, wardrobe, concierge threads/messages, appointment-change requests, notifications, lifecycle events, and saved styles.
- Update only permitted profile columns.
- Insert/delete only their own saved style links.
- Update only notification read state fields.

Authenticated customers may not directly:
- Insert or update bespoke requests.
- Set quote, approval, operational status, conversion state, or staff/internal notes.
- Insert/update measurement history or verification state.
- Create/update orders, payments, wardrobe items, appointment operational state, lifecycle events, or system notifications.
- Create concierge messages with a staff identity.
- Execute the trusted conversion, verified-payment, wardrobe, or other service-role RPCs.

The migration combines table grants with row ownership policies; policies are explicitly scoped TO authenticated. Public intake tables have RLS enabled and no anon/authenticated table privileges. Customer A versus Customer B isolation is encoded through auth.uid() ownership predicates and relational guards. Practical cross-user verification remains part of the live pgTAP/deployment step.


D. SERVER AUTHORITY LAYER

Introduced server-only Supabase administration and domain services. SUPABASE_SERVICE_ROLE_KEY is read only by src/lib/server/supabase-admin.ts and is not a NEXT_PUBLIC variable or imported by Client Components.

Trusted operations introduced:
- Create a new measurement version transactionally.
- Submit a bespoke request and optional appointment request atomically.
- Create an appointment reschedule/cancellation request.
- Create concierge threads and customer replies after ownership/status checks.
- Create system notifications from trusted workflows.
- Persist contact enquiries and public fitting requests.
- Initialize a future payment only after trusted order/ownership/balance checks.
- Convert an eligible trusted-price request into an order atomically for future Phase 5 use.
- Record provider-verified payments idempotently for future integration.
- Create or return a wardrobe item only for a completed order.

The future staff operations are not exposed to customers and remain unused until a real Phase 5 staff authorization layer exists.


E. BESPOKE REQUEST REPAIR

- The browser no longer creates orders, sets quotes, or marks requests converted.
- Submitted requests are persisted through an authenticated Server Action and a service-role-only transactional database function.
- The server validates and normalizes customer contact, garment, fabric, colour, fit, measurements, dates, appointment details, and durable upload metadata.
- A selected appointment is created in the same transaction as the request.
- The configurator awaits authoritative persistence, reports errors, and clears/navigates only after success.
- A failed submission preserves the draft and remains retryable.
- Pricing Ready may display a trusted stored quote, but customer-side conversion is unavailable.
- Draft editing remains local before submission. Submitted/under-review records are read-only to customers.
- Guest bespoke configuration remains explicitly local/non-authoritative; it cannot create an order, payment, trusted status, or verified record.


F. MEASUREMENT REPAIR

- Customers cannot update historical rows or self-assign TSquare verification.
- A change creates a new version, advances the version number, marks the prior current row inactive, and sets the new row current in one transaction protected by an advisory lock.
- Database indexes enforce one current record and unique Customer + Version.
- Saved/manual/scheduled submission snapshots include values, unit, method, source measurement ID/version, verification state, fit preference, and snapshot timestamp.
- Order and wardrobe views use their stored historical snapshots instead of dynamically reading the current customer profile.


G. APPOINTMENT REPAIR

- Customers cannot directly update confirmed date/time, location, completion, or operational status.
- Initial appointment requests are created by the trusted request transaction with status requested.
- Reschedule/cancellation requests verify appointment ownership server-side and force pending_review.
- The original appointment remains unchanged until a future trusted staff decision.
- Change-history foreign keys now use RESTRICT instead of cascading away history.


H. PAYMENT REPAIR

REAL PAYMENT PROVIDER ACTIVE: NO.

- The fake sandbox success adapter and browser-created successful payments were removed.
- Online payment initialization uses an explicit unavailable provider that always fails closed with truthful customer wording.
- A click cannot create a successful Payment, alter Amount Paid/Balance, or generate a verified receipt.
- Receipts render only for stored successful payment records.
- Financial calculations use integer minor units (kobo); compatibility numeric NGN fields are converted deliberately at trusted boundaries.
- The future verified-payment RPC derives customer ownership from the order, checks the trusted order total/outstanding balance, requires a verified provider timestamp, locks on Provider + Reference, detects conflicting replay data, and emits notification/lifecycle records atomically.
- No Paystack, Flutterwave, or other provider was selected.

Future provider boundary: implement a deliberate adapter, server-side initialization, signature-verified webhook, provider verification, reconciliation/refunds, and only then call record_verified_payment.


I. WARDROBE REPAIR

- Browser/customer wardrobe creation was removed.
- A service-role-only operation accepts only Completed orders.
- Customer identity and garment/configuration/measurement history are copied from the trusted order.
- Order ID uniqueness and relationship guards prevent duplicates and customer mismatch.
- Repeated completion calls return the existing item safely.
- Wardrobe creation produces a trusted notification and lifecycle event.
- Order Similar now uses the valid style slug; Use as Inspiration validates and loads only a wardrobe item already returned through the authenticated customer's RLS-scoped dataset.


J. SAVED LOOKS REPAIR

- Guests continue to use localStorage.
- Authenticated customers hydrate from Supabase as the authority.
- Guest saves merge once after login, deduplicate through Customer + Style uniqueness/upsert, and clear locally only after successful persistence.
- New saves/removals await the database and rollback optimistic UI on failure.
- Deleted authenticated saves are not rebuilt from stale local guest state.


K. CONCIERGE REPAIR

- Database-generated UUIDs replace timestamp/string IDs.
- Creation waits for the database result and uses the returned request ID.
- Category, subject, message, and related identifiers are server-validated.
- Related request/order/appointment ownership is verified in the database operation.
- Sender ID is the authenticated customer; sender type is forced to customer.
- Replies require an owned thread in an allowed open state.
- Seeded staff conversations are no longer substituted for real empty accounts.


L. STORAGE

- bespoke-references is private.
- Authenticated paths use <customer-id>/<draft-id>/<uuid>.<approved-extension>.
- Storage policies enforce bucket, first-folder customer identity, and owner_id for reads/updates/deletes.
- Client and server validation enforce JPEG/PNG/WebP, 10 MB per file, six-file maximum, durable storage path, valid UUID metadata, and authenticated ownership prefix.
- Uploads and removals inspect errors; failed batches attempt cleanup; temporary object URLs are revoked.
- Request rows store durable path/filename/size/MIME metadata, not blob URLs.


M. MOCK DATA REMOVAL

Removed normal-production fallbacks for:
- Orders and financial balances.
- Successful/pending payments and receipts.
- Verified measurement profiles.
- Confirmed appointments.
- Wardrobe garments.
- Operational notifications.
- Concierge requests and staff replies.
- Bespoke conversion success.

Demo behavior is available only when NEXT_PUBLIC_TCC_DEMO_MODE=true in a non-production process, and its account datasets are empty rather than authoritative-looking business fixtures.


N. CONTACT / FITTING PERSISTENCE

- Contact submissions are server-validated and inserted into private contact_enquiries.
- Public fitting submissions are server-validated and inserted into private public_fitting_requests.
- Authenticated fitting requests associate the authenticated customer when available; guest requests remain safe intake records.
- Fitting status is requested, not confirmed.
- No setTimeout success remains.
- Database/configuration errors produce a user-safe error and do not switch the UI to success.


O. AUTH / MIDDLEWARE REPAIRS

- Protected account routes fail closed when Supabase configuration is absent.
- Missing configuration no longer silently enables mock authentication.
- Demo mode requires an explicit development-only flag.
- Auth callback and authenticated redirects accept only safe same-origin internal paths.
- Code exchange/recovery errors map to safe customer-facing states.
- Password recovery distinguishes valid session, missing/expired link, update failure, and success without exposing raw backend messages.
- Account routes include noindex/nofollow/noarchive handling.
- metadataBase uses NEXT_PUBLIC_SITE_URL with a localhost development fallback; no unconfirmed production domain was invented.
